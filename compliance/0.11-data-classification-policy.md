## 2. Principles

1. **1 Fact, 1 Name:** DataClass tag matches exactly across Audit, Diagrams, RoPA, DPIAs, Terraform, and this policy. No new tags are invented.
2. **Default to higher class:** Where classification is unsure, classification is higher, not lower. Where data contains one Sensitive field, the whole file is Restricted-PII + Sensitive, not Restricted-PII.
3. **Tag at intake:** Classification happens when data is created or received, not later. Lambda classifies at S3 intake. Form classifies at submission. No manual download then classify.
4. **Least privilege:** Access is by DataClass + Group, not by person. Sales-group sees Restricted-PII for Flow 1. HR-group sees Restricted-PII + Sensitive for Flow 2. No one sees both unless DPO approves.
5. **Pseudonymisation is not declassification:** Pseudonymised data is still personal data. `sha256_hashed_id` is still Restricted-PII, until it is truly anonymised and re-identification is impossible. Pseudonymised data is not downgraded to Internal.
6. **Pseudonymisation is a technique, not a RetentionDays value:** RetentionDays is 90, 180, 365, 1825. RetentionDays is not Pseudonymised.

## 3. DataClass Tags — Canonical List

**Only these 5 tags exist. SPII is not a DataClass tag. PII, Sensitive, Confidential-PII, or any other tag are not DataClass tags.**

| DataClass Tag | What It Means | Examples at AfterCast AI |
| :--- | :--- | :--- |
| `Public` | Public marketing, no PII, can be published | Public website copy, public blog, public job advert with no applicant data |
| `Internal` | Internal docs, no PII, not for public | Internal runbooks, architecture diagrams with no PII, DSR logs with hashed ID only, meeting notes with no PII |
| `Confidential` | Business confidential, no PII, harm where leaked | Pricing, contracts, vendor terms, roadmap, source code with no secrets, internal financial forecasts with no PII |
| `Restricted-PII` | Customer PII, EU, identifiable, harm where leaked is phishing, fraud, spam | Flow 1: LuxeMart UK, 12,000 EU, Name, Email, Phone, Delivery Address, Loyalty ID, Purchase History |
| `Restricted-PII + Sensitive` | Applicant / employee PII + Sensitive, NIN, BVN, Passport, Bank Details, harm where leaked is identity takeover, bank fraud, SIM swap | Flow 2: HR Applicants, 143 NG, CV, NIN, BVN, Passport scan, Home Address, Bank Details |

**Choosing a tag:**

- Data contains Name, Email, Phone, Address, Loyalty ID, Purchase History → `Restricted-PII`
- Data contains NIN, BVN, Passport, Bank Details, or any national ID / financial ID → `Restricted-PII + Sensitive`, even where it also contains Name, Email, Phone. Sensitive wins.
- Data contains both customer PII and Sensitive → `Restricted-PII + Sensitive`
- Data contains no PII, but business harm where leaked → `Confidential`
- Data contains no PII and no business harm → `Internal`
- Data is already public → `Public`

**Examples that are often misclassified:**

| Data | Wrong Tag | Correct Tag | Why |
| :--- | :--- | :--- | :--- |
| LuxeMart CSV with Name, Email, Purchase History | `Internal` or `Confidential` | `Restricted-PII` | Contains PII, tag is Restricted-PII |
| HR Sheet with NIN, BVN | `Restricted-PII` | `Restricted-PII + Sensitive` | Contains Sensitive, tag is + Sensitive |
| `model.pkl` trained on raw emails | `Internal` or `Confidential` | `Restricted-PII` | Model memorises emails, model is PII |
| DSR log with hashed ID only, no raw email | `Restricted-PII` | `Internal` | Hashed ID only, no raw PII, where mapping is separate and access is controlled. Where mapping is in same file, tag is Restricted-PII. |
| S3 logs with raw email in log line | `Internal` | `Restricted-PII` | Log contains PII, log is redacted or re-tagged |
| Mapping table email → hashed_id | `Internal` | `Restricted-PII + Sensitive` where Flow 2, `Restricted-PII` where Flow 1 | Mapping re-identifies, tag is highest class of data it maps |

### 5.2 Untagged Data

1. Stop. No forwarding, downloading, or sharing of untagged data.
2. Classify it using Sec 3. Where unsure, classify higher.
3. Tag it, or move it to S3 with correct tag, via WorkMail + pre-signed URL, not via personal Gmail.
4. Tell DPO Kenneth Pratt. DPO logs it in RoPA Change Log.
5. Where it is Restricted-PII or Restricted-PII + Sensitive in personal Gmail, Dropbox, WhatsApp, Sheet, QNAP, USB, or GitHub, it is treated as a potential breach. Breach Playbook applies, DPO is notified within 24h internal.

## 8. Terraform Enforcement — How Tags Are Enforced, Not Only Policy

Policy alone does not enforce. Terraform enforces. The following is in Phase 1 + Phase 2 Terraform.

### 8.1 SCPs — AWS Organizations

- Deny `s3:PutObject` where `aws:RequestTag/DataClass` is missing.
- Deny `s3:PutObject` where `aws:RequestTag/RetentionDays` is missing.
- Deny any action in any region except `eu-west-1` and `eu-west-2` for PII. Deny `us-*` for PII.
- Deny `s3:PutBucketPublicAccessBlock` disable, Deny `s3:PutBucketAcl` public, Deny `s3:PutObjectAcl` public.
- Deny `iam:CreateUser` without MFA, Deny `s3:DeleteBucket` without MFA Delete for HR + Prod buckets.

### 8.2 S3 Bucket Policies

- `s3://aftercast-prod-restricted-pii-eu-west-1/` — Deny PutObject where `DataClass` is not `Restricted-PII`. Deny PutObject where `RetentionDays` is not `365`. Deny GetObject where `aws:PrincipalTag/Group` is not `sales-group` and is not `dpo-audit`. Deny DeleteObject except Lifecycle + DSR role.
- `s3://aftercast-hr-restricted-pii-eu-west-1/` — Deny PutObject where `DataClass` is not `Restricted-PII + Sensitive`. Deny PutObject where `RetentionDays` is not in `180, 1825`. Deny GetObject where `aws:PrincipalTag/Group` is not `hr-group` and is not `finance-group` and is not `dpo-audit`. Deny DeleteObject except Lifecycle + DSR role.
- Both buckets: Block Public Access ON, Versioning ON, KMS CMK, Object Lock ON for audit logs, VPC Endpoint only, TLS 1.2 only.

### 8.3 Lake Formation

- Flow 1: Database `prod`, Table `forecasting_features`, Grant SELECT to `sales-group` only, Columns `hashed_id, purchase_features` only, No `SELECT *`.
- Flow 2: Database `hr`, Table `applicants`, Grant SELECT to `hr-group` only, Grant SELECT payroll columns to `finance-group` only, No `SELECT *` for Sensitive columns without DPO approval.
- Mapping table: Grant SELECT to `dpo-audit` only, not Data Science, not Sales, not HR.

### 8.4 Lifecycle + Retention

- Flow 1: S3 Lifecycle Delete raw CSV after 365 days, Transition logs to Glacier Deep Archive after 90 days, Keep logs 6 years, PII not kept 6 years.
- Flow 2 Rejected: S3 Lifecycle Transition to Glacier after 30 days, Delete after 180 days.
- Flow 2 Hired: S3 Lifecycle Transition to Glacier after 1 year, Transition to Deep Archive after 6 years, Delete after 6 years + audit proof.
- All: S3 Inventory + CloudTrail + Macie proof, kept 6 years in Glacier Deep Archive, hashed ID + DSR ID only, not raw PII.

### 8.5 Where Terraform Blocks

Where Terraform or AWS blocks a PutObject, GetObject, or DeleteObject, no workaround via personal Gmail, Dropbox, WhatsApp, Sheet, QNAP, USB, or GitHub applies. Engineering + DPO are notified. The block is the control working. Workaround is a breach.

### 13.1 Numbering System — Rules

- Phase 0 docs use `0.x`, sequential from `0.0` to `0.18`, with no gaps. `0.0` is prerequisites. `0.1` is Shadow IT Inventory. `0.2` is Audit Report. `0.3` is RoPA. `0.4` is DPIA — HR. `0.5` is DPIA — Profiling. `0.6` is Business Case. `0.7` is Foundational Roadmap. `0.8` is Roadmap. `0.9` is Glossary. `0.10` is Appendix B. `0.11` is this file, Classification. `0.12` is Retention. `0.13` is Compliance Mapping. `0.14` is DPA + TIA. `0.15` is Privacy Notice. `0.16` is Legacy Sanitization Certificate. `0.17` is Appendix G. `0.18` is Appendix H.
- Phase guides use `phase-N`, for example `phase-1-organization-identity.md`. They are not `0.x`, because they belong to Phases 1 to 10, not Phase 0.
- Evidence uses `phase-N`, for example `evidence/sections-after/phase-1/`. It is not `0.x`.
- Terraform uses `phase-N`, for example `terraform/phases/phase-1/`. It is not `0.x`.
- File names keep bare `before` / `after` where they appear: `audit-before`, `sections-after`, `0.18-appendix-h-before-vs-after.md`.

## 14. Rules — 1 Fact, 1 Name

- **1 Fact, 1 Name:** Character, Location, Count, DataClass match exactly across Inventory, Diagram, Findings, RoPA, DPIA, Tables, Appendix B, Roadmap. Auditor Ctrl+F finds the same name everywhere.
- **One fact, one file:** Glossary lives once in `0.9-glossary.md`. Compliance mapping lives once in `0.13-compliance-mapping.md`. Other docs link.

- **Audit Report name:** Security and Privacy Audit Report, or Audit Report, with no number in the name.
- **Phase vs Wave vs Section:** Phase = 0 to 10 roadmap block, 11 Phases. Wave = 1 to 5 delivery increment, 5 Waves. Section = single build unit inside a Phase, 56 Sections in the Roadmap.
- **Naming:** `phase-1` format throughout. `terraform/phases/phase-1/`, `docs/phases/phase-1-...`, `evidence/sections-after/phase-1/`.
- **Numbering:** All doc filenames use the numbering system in Sec 13.1. Phase 0 docs use `0.x`. Phase guides, evidence, and Terraform use `phase-N`.
- **Email separator:** Em-dash style. `Personal Gmail: funmi.personal@gmail.com — Funmi Daniels (Sales, AE)` and `WorkMail: funmi.daniels@aftercast.ai — Funmi Daniels (Sales, AE)`.
